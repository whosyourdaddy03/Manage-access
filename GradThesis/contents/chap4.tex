\chapter{系统构建与技术实现}

在第三章给出的需求与架构基础上，本章介绍系统的具体构建过程，包括对 jMAVSim 的六项改造、编队巡游与尾随相机的实现，以及算法端、显示端、通信协议与部署运维等实现细节。

\section{jMAVSim 改造}

\subsection{改造需求}

原版 jMAVSim 只认一架由 PX4 控制的多旋翼，相机固定跟着这架飞机，既没有独立的“目标机”，也没有可自由摆放的“护航相机”，真值广播与视频推流同样缺席。要把它当作反无人机场景的发生器，需要补上六件事：

（1）另设一架由脚本驱动、沿预定航线飞行的目标机；

（2）增设一台独立的护航相机，始终注视目标机，模拟地面或伴飞观测平台；

（3）把目标机真值（位置、速度、相机位置）广播出去，供算法端评估；

（4）将护航相机画面编码为 JPEG，经 TCP 推送；

（5）支持纯离屏渲染，不再依赖窗口系统；

（6）生成城市级场景，含建筑、树木、道路与广场。

\subsection{脚本目标机}

脚本目标机由新增的 \texttt{ScriptedQuad} 类实现，它继承 \texttt{KinematicObject}，按时间参数化的航迹改写自身位置与速度。航迹以 Catmull-Rom 样条串起三维空域内的 22 个航点。选这种样条有很实际的理由：曲线严格穿过每个控制点，段间切线连续，巡游路线不会出现折角。

记四个相邻控制点为 $\mathbf{P}_{i-1},\mathbf{P}_i,\mathbf{P}_{i+1},\mathbf{P}_{i+2}$，段参数 $t\in[0,1]$，样条点可写成

\begin{equation}
\mathbf{C}(t) = \frac{1}{2}\Big[
2\mathbf{P}_i + (-\mathbf{P}_{i-1}+\mathbf{P}_{i+1})t
+ (2\mathbf{P}_{i-1}-5\mathbf{P}_i+4\mathbf{P}_{i+1}-\mathbf{P}_{i+2})t^2
+ (-\mathbf{P}_{i-1}+3\mathbf{P}_i-3\mathbf{P}_{i+1}+\mathbf{P}_{i+2})t^3
\Big].
\label{eq:catmull}
\end{equation}

对 $t$ 求导得到切线，飞行方向与速度方向由此确定：

\begin{equation}
\mathbf{C}'(t) = \frac{1}{2}\Big[
(-\mathbf{P}_{i-1}+\mathbf{P}_{i+1})
+ 2(2\mathbf{P}_{i-1}-5\mathbf{P}_i+4\mathbf{P}_{i+1}-\mathbf{P}_{i+2})t
+ 3(-\mathbf{P}_{i-1}+3\mathbf{P}_i-3\mathbf{P}_{i+1}+\mathbf{P}_{i+2})t^2
\Big].
\label{eq:catmull_deriv}
\end{equation}

航点范围是反复调整后的结果，目的是让目标始终待在护航相机的有效视野与检测距离之内：$x\in[-9,9]$\,m，$y\in[-38.5,-29.5]$\,m，$z\in[-16,-9.5]$\,m（NED，负值表示高度）。每段速度 0.8--2.8\,m/s，段内做加减速（见第~\ref{sec:formation} 节）。

\subsection{护航相机}

护航相机对应 \texttt{CameraRig} 类，同样继承 \texttt{KinematicObject}。它和原版固定相机的工作方式不一样：每帧读取目标机的实际位置与速度，先算出期望机位，再用一阶低通慢慢靠过去，细节留到第~\ref{sec:formation} 节交代。

相机水平视场取 60\textdegree，1280 宽的图像对应焦距

\begin{equation}
f = \frac{W/2}{\tan(\mathrm{FOV}_h/2)} = \frac{640}{\tan30^{\circ}}\approx1108.5\ \text{px}.
\label{eq:fx}
\end{equation}

这个数值与算法端的测距公式共用同一套参数含义，仿真与实拍才有可比性。

\subsection{真值广播}

真值由新增的 \texttt{TruthBroadcaster} 线程发出，频率 50\,Hz，目的端口 UDP 14680，报文是文本单行：

\begin{verbatim}
t=<ms> tp=<x,y,z> tv=<vx,vy,vz> ep=<x,y,z> cp=<x,y,z>
\end{verbatim}

其中 \texttt{t} 是仿真时间戳，\texttt{tp} 与 \texttt{tv} 分别是目标的位置与速度，\texttt{ep} 为自身机位置，\texttt{cp} 为相机位置；坐标系取 NED，长度单位为米，速度单位为米每秒。视频帧与真值走的是两条独立链路，对齐只能依靠时间戳。若按“先到先配”的办法拼接，几十毫秒的偏差足以让距离曲线冒出毛刺。

\subsection{离屏渲染与帧流}

原版 jMAVSim 把画面画在 Java3D 的窗口画布上。WSL 环境里，WSLg 的共享内存偶尔出状况，跑久了画面变白，进程也可能直接退出。本文改用纯离屏渲染，步骤有四步：

（1）建一个离屏 \texttt{Canvas3D}，不绑定任何 \texttt{Frame}；

（2）每帧调用 \texttt{render}，把场景画进离屏缓冲区；

（3）用 \texttt{ImageIO} 把缓冲区编码成 JPEG；

（4）经 TCP 连接推送“头部行 + 二进制数据”。

头部行格式为

\begin{verbatim}
<seq> <timestamp_ms> <width> <height> <nbytes>
\end{verbatim}

接收端先读一行文本，从中取出字节数，再按这个长度精确读取 JPEG。文本头既躲开了 TCP 粘包，也让接收端能凭序号跳变发现丢帧。

有一点容易漏掉：离屏渲染必须屏蔽窗口画布的 \texttt{glXSwapBuffers} 调用，软件渲染下这一调用会直接导致 JVM 崩溃。附带的好处是，画面不随窗口最小化而暂停，帧流始终连续。

\subsection{场景构建}

城市场景由 \texttt{SceneBuilder}、\texttt{SceneBuilding}、\texttt{SceneTree} 等类程序化生成，含四类要素：

（1）\textbf{地面}：大范围草地纹理，中央铺 140$\times$110\,m 的浅灰水泥广场，广场覆盖整条巡游轨迹，目标下方的材质与地图显示因此保持一致；

（2）\textbf{建筑}：53 栋建筑分列目标飞行走廊两侧，高度一律低于 8\,m，避免遮挡目标检测；立面使用程序化贴图，按楼层与开间重复，色调压暗，远看不像一排白色盒子；

（3）\textbf{树木}：82 棵近景树与 90 棵远景树，近景树冠由 6 个错位椭球堆叠而成，远景树线用来收拢地平线；

（4）\textbf{天空}：2048$\times$1024 的蓝天白云全景贴图，替换原版 jMAVSim 自带的公园照片背景。

场景对象合计约 149 个。建筑与树木的坐标逐一核对过，没有一栋楼、一棵树落进护航相机与目标机之间的视线通道。



\section{编队巡游与尾随相机}
\label{sec:formation}

\subsection{设计目标}

早期版本里，目标机与相机各走各的路径，彼此之间没有主动与被动的分别。画面看上去要么像相机被粘在目标上，要么像目标追着相机飞，与真实监视场景中的追踪感相去甚远。为把“地面或伴飞平台追踪目标”这件事模拟得像样一些，本文实现了编队巡游与尾随相机，规则有三条：

（1）目标机是主动飞行方，按预设航线飞行并做加减速；

（2）相机是被动追随方，根据目标的实际位置与速度计算期望机位，带滞后地跟随；

（3）相机瞄准一个“滞后于目标”的瞄准点，使目标在画面中自然漂移，而不是死锁在中心。

\subsection{目标机航迹与加减速}

目标机的运动由两层叠加而成：局部样条航迹与全局编队偏移。局部样条定义在以相机为原点的局部空域内，负责把检测距离维持在 3--10\,m；全局偏移则把整段航迹搬到城市的椭圆路线上：

\begin{equation}
n(a) = C_X + R_X\sin a,\qquad e(a) = C_Y + R_Y(1-\cos a),
\label{eq:ellipse}
\end{equation}

椭圆中心取 $C_X=8$\,m、$C_Y=-4$\,m，半轴 $R_X=18$\,m、$R_Y=22$\,m，$a$ 是随速度累加的角度参数。周长约 126\,m，按 2\,m/s 巡游，一圈约 63\,s。

真实飞行不会匀速。本文对每段参数 $t$ 做 smoothstep 重参数化：

\begin{equation}
u = (1-\gamma)t + \gamma\,t^2(3-2t),\qquad
\frac{du}{dt} = (1-\gamma)+\gamma\cdot6t(1-t),
\label{eq:smoothstep}
\end{equation}

其中 $\gamma=0.75$ 表示变速强度。端点处 $du/dt=1-\gamma=0.25$，速度降到段均速的 25\%，相当于减速过弯；中点处 $du/dt=1-\gamma+1.5\gamma=1.375$，速度升到段均速的 137.5\%，相当于加速出弯。速度向量沿切线方向乘以 $du$：

\begin{equation}
\mathbf{v} = \frac{\mathbf{C}'(u)}{\|\mathbf{C}'(u)\|}\cdot v_{seg}\cdot\frac{du}{dt}.
\label{eq:velocity}
\end{equation}

这样一来，真值广播里的速度与目标的实际运动对得上，评估速度对检测与测距的影响才有意义。实测速度在 0.21--2.95\,m/s 之间连续变化，不再是人为设定的匀速。

\subsection{尾随相机动力学}

期望机位定在目标速度反方向、距离 $d$ 处，并比目标略低：

\begin{equation}
\mathbf{p}_{des} = \mathbf{p}_{t} - \hat{\mathbf{v}}_{t}^{xy}\cdot d + \begin{bmatrix}0\\0\\\Delta z\end{bmatrix},
\label{eq:cam_desired}
\end{equation}

其中 $\hat{\mathbf{v}}_t^{xy}$ 为目标水平速度的单位方向，$\Delta z=1.2$\,m（NED 下取正，意味着相机低于目标 1.2\,m），由此形成轻微仰视。检测模型在侧视与仰视下更稳定，这个高度差是有意保留的。距离 $d$ 随目标速度伸缩：

\begin{equation}
d = d_0 + \min\left(k_v\|\mathbf{v}_t^{xy}\|,\,d_{max}\right),
\label{eq:cam_dist}
\end{equation}

本文取 $d_0=5.0$\,m、$k_v=0.5$\,s、$d_{max}=1.0$\,m，速度每增加 2\,m/s，相机后退 1\,m，额外距离封顶 1\,m。

相机位置并不直接跳到期望机位，而是以时间常数 $\tau=0.6$\,s 做一阶低通：

\begin{equation}
\mathbf{p}_{c,k} = \mathbf{p}_{c,k-1} + \left(1-e^{-\Delta t/\tau}\right)\left(\mathbf{p}_{des,k}-\mathbf{p}_{c,k-1}\right).
\label{eq:cam_lpf}
\end{equation}

滞后正是追踪感的来源：目标转弯，相机需要一定时间才转到新的尾随方向，画面里目标先偏向一侧，随后被追回；目标加速，相机暂时落后，距离短暂拉大，再慢慢收敛。

\subsection{瞄准点滞后}

如果相机始终对准目标本体，目标会钉在画面正中，看上去像吸附。本文另设一个瞄准点（AimPoint），它是目标位置的滞后副本，

\begin{equation}
\mathbf{p}_{aim,k} = \mathbf{p}_{aim,k-1} + \left(1-e^{-\Delta t/\tau_{aim}}\right)\left(\mathbf{p}_{t,k}-\mathbf{p}_{aim,k-1}\right),
\label{eq:aim}
\end{equation}

其中 $\tau_{aim}=0.45$\,s。相机对准 $\mathbf{p}_{aim}$ 而非 $\mathbf{p}_t$，目标便在画面中自然漂移：领先于瞄准点时，它出现在中心前方；转向时，它滑到画面一侧。这种漂移与真实监视画面里操作员手动跟踪、目标略微偏离中心的观感一致。

\subsection{验证结果}

本文用真值 UDP 抓包统计了尾随相机的实际距离与目标速度：

（1）距离：100 个样本，最小 5.22\,m，中位 5.29\,m，最大 5.41\,m；

（2）速度：120 个样本，最小 0.94\,m/s，中位 1.40\,m/s，最大 1.57\,m/s；另一轮长时统计为 0.21--2.95\,m/s。

距离稳定在 5.2--5.4\,m，正好落在检测模型的可靠工作区间；速度连续变化，加减速清晰可见。图~\ref{fig:dashboard_live} 是运行中的界面截图，目标在光电画面里略微偏离中心，与尾随跟踪的观感相符。

\subsection{设计约束}

尾随相机的参数还要受检测模型约束。实验中留意到，一旦相机俯视目标（目标低于相机 3--8\,m），检出率会从 73\%--77\% 掉到 22\%--37\%；俯视视角下目标投影变形，旋翼与机身叠在一起，模型难以分辨。因此本文让相机始终略低于目标（$\Delta z=1.2$\,m），保持轻微仰视。这件事说明，仿真场景不能只求画面好看，还要服从算法的适用域。

\section{算法端实现}

\subsubsection{视频源抽象}

三种输入在算法端被统一成“帧源”接口，只暴露 \texttt{open}、\texttt{read}、\texttt{close} 三个方法。离线视频与 USB 摄像头都基于 OpenCV 的 \texttt{VideoCapture}，区别在于后者还要协商设备索引与分辨率；TCP 帧流源自己实现协议解析，并带有断线重连。

TCP 帧流源的读取按以下步骤进行：

（1）连上服务器地址与端口；

（2）循环读一行文本头，取出序号、时间戳、宽高与字节数；

（3）按字节数取走 JPEG 数据；

（4）用 \texttt{cv2.imdecode} 解码成 BGR 图像；

（5）遇到序号跳变，把丢帧数记下来。

读取设了超时，网络抖动时不至于无限期阻塞；超时后关闭连接，再从新连接继续。

\subsubsection{检测模块}

检测模块包住 Ultralytics 的 \texttt{YOLO} 类，对外只留一个 \texttt{detect(frame)} 方法。实现里做了三处调整：

（1）\textbf{固定输入尺寸}：一律缩放到 640$\times$640，动态尺寸引起的重复编译就此消失；

（2）\textbf{关闭冗余输出}：置 \texttt{verbose=False}，日志开销随之下降；

（3）\textbf{半精度推理}：GPU 上走 FP16，速度提升约 30\%，精度损失可以忽略。

NMS 之后候选框按置信度从高到低排序，算法端只保留前 20 个，极端场景下的后处理开销因此可控。

\subsubsection{状态机与滤波}

状态机的实现与第五章的伪代码一一对应，核心是 \texttt{update(detections, dt)} 方法。滤波器借 NumPy 完成矩阵运算，预测、更新、自适应噪声估计与数值保护都在其中。

实现时特别留意了三点：

（1）\textbf{时间步长}：用实际时间戳差值，不写死 1/30\,s，不同帧率都能兼容；

（2）\textbf{数值稳定}：协方差矩阵每次更新后做对称化，浮点误差累积不会把矩阵推成非正定；

（3）\textbf{状态重置}：目标丢失时清空滤波器与轨迹缓存，旧状态不会污染新目标。

\subsubsection{数据记录}

每帧处理完，算法端把结果字典追加到 CSV。表头在文件创建时写一次，其后逐行追加。磁盘 I/O 有可能拖住处理线程，记录因此采用缓冲写入，每 50 帧刷新一次；程序退出时执行 \texttt{close}，保证最后一段数据落盘。

CSV 以运行时间命名，同时存一份运行参数（模型、门限、尺寸、输入源），日后复现时不必凭记忆。本文所有实验数据都出自这些文件，分析脚本直接读取它们生成表格与图。

\subsubsection{结果输出}

算法端用 UDP 把 JSON 报文发给显示端，发送频率与处理帧率一致。报文覆盖表~\ref{tab:result_fields} 的主要字段，另外附带相机位置、时间戳与状态机计数。显示端按 \texttt{frame\_id} 去重，只渲染最新的一帧。

紧凑 JSON 去掉了空格，单帧约 300 字节；30\,fps 下带宽约 9\,KB/s，局域网里几乎感觉不到。

\section{显示端实现}

\subsubsection{界面布局}

显示端分三个页签：目标态势、检测回放与参数设置。目标态势页是主界面（图~\ref{fig:dashboard_satellite}），按位置分成五块：

（1）\textbf{顶部状态栏}：系统名称、运行状态、时间与告警等级；

（2）\textbf{左侧信息栏}：目标卡片（类型、距离、置信度、威胁等级）、跟踪状态灯与链路状态；

（3）\textbf{中央地图}：卫星影像底图，标注目标位置、航迹、视野扇形与距离环；

（4）\textbf{右侧仪表}：距离卡、方位罗盘与行动控制按钮；

（5）\textbf{底部数据条}：距离、方位、俯仰、速度、置信度、状态、帧号等 8 项实时数据。

\subsubsection{地图实现}

地图用 QtWebEngine 嵌入本地 HTML，页面加载 Leaflet 与 Esri 卫星瓦片。Python 端通过 \texttt{runJavaScript} 把数据推进页面，页面负责挪动标记、改写折线顶点、调整圆环半径。

坐标转换是地图部分的关键。算法端算出的目标位置在相机坐标系下，显示端要把它落成经纬度，本文采用局部切平面近似：

\begin{equation}
\phi = \phi_0 + \frac{x_{north}}{R_e},\qquad
\lambda = \lambda_0 + \frac{x_{east}}{R_e\cos\phi_0},
\label{eq:geo}
\end{equation}

其中 $(\phi_0,\lambda_0)$ 是地图锚点（默认取相机机位），$R_e$ 为地球半径，$x_{north},x_{east}$ 是以相机为原点的北向、东向位移。几百米范围内，该近似误差小于 0.1\,m，监视用途足够。

叠加到地图上的元素有六类：

（1）\textbf{观测站标记}：相机位置，随编队移动；

（2）\textbf{目标标记}：实心圆对应 LOCKED，虚线空心圆对应 COAST；

（3）\textbf{预测点}：青色菱形，以虚线连到目标标记，代表 1\,s 后的预测位置；

（4）\textbf{视野扇形}：以相机为顶点、沿视轴方向张开，示意相机覆盖范围；

（5）\textbf{距离同心环}：以相机为圆心，标出 50\,m、100\,m 等距离；

（6）\textbf{航迹折线}：连接目标的历史位置，透明度随新旧渐变。

\subsubsection{光电画面}

光电区域显示算法端回传的带框视频帧，上面再压几层标注：

（1）\textbf{中心准星}：十字加圆环，标示光轴方向；

\subsubsection{仪表与告警}

距离卡用大字号显示滤波后距离，下方小字补上原始距离、预测距离与相对高度。方位罗盘以指针指示方位，外圈是角度刻度，内圈显示俯仰角。跟踪状态灯用三种颜色区分 SEARCH（灰）、LOCKED（绿）与 COAST（黄），旁边附状态切换计数。

威胁分级根据距离与接近速度计算：

\begin{equation}
\mathrm{Level} = \begin{cases}
\text{高}, & Z<50\ \text{m}\ \text{或}\ v_{closing}>3\ \text{m/s},\\
\text{中}, & Z<150\ \text{m}\ \text{或}\ v_{closing}>1\ \text{m/s},\\
\text{低}, & \text{其他}.
\end{cases}
\label{eq:threat}
\end{equation}

阈值可按任务配置改动。等级为“高”，顶部横幅转红并闪烁，同时播放提示音；“中”为橙色；“低”为绿色。告警记录一并写入 CSV，事后可以回看。

\section{通信协议}

\subsubsection{视频帧协议}

TCP 帧流协议由“一行文本头 + 二进制数据”拼成。头部依次是序号、时间戳、宽度、高度、字节数，以空格分隔，以换行收尾。接收端读完头部，按字节数取走 JPEG。文本头牺牲了一点紧凑性，换来的是可调试性：用 telnet 连上去就能看到每帧的元信息，字段含义也不言自明。

\subsubsection{真值协议}

UDP 真值报文是单行文本，键值对之间以空格分隔。接收端按空格切开，再按等号取键与值。协议简单，扩展也容易，新加字段不会让旧版接收端解析失败。

\subsubsection{结果协议}

结果报文用 JSON。显示端与上级系统未必用同一种语言，JSON 的支持面最广；字段可读，联调时省去不少猜测。报文约 300 字节，远小于 UDP 的 1472 字节 MTU，不需要分片。

\section{配置与持久化}

配置分三类：

（1）\textbf{算法参数}：模型路径、输入尺寸、置信度门限、等效尺寸、空域先验、滤波噪声；

（2）\textbf{通信参数}：TCP 地址与端口、真值 UDP 端口、结果 UDP 地址与端口；

（3）\textbf{界面参数}：地图锚点、地图模式、数据面板开关、告警阈值。

三类参数放在同一个 JSON 文件里，呈嵌套字典结构。启动时读取，缺字段用默认值补上；保存时把不认识的字段原样留下，版本升级不会把旧配置冲掉。这种宽松读写在长期使用中省去了大量兼容性麻烦。

\section{回放与自动化测试}

\subsubsection{14 用例测试框架}

为了把功能验证固定下来，本文设计了 14 个自动化用例，覆盖六类场景：

（1）\textbf{基线检测}（C01--C03）：用仿真闭环录像核对检测、跟踪与测距的基本正确性；

（2）\textbf{真实场景}（C04--C05）：用真实无人机录像考察跨域能力与远距离边界；

（3）\textbf{门限扫描}（C06--C08）：改动置信度门限，观察锁定率与保持率如何变化；

（4）\textbf{尺寸敏感}（C09--C10）：改动等效尺寸，验证测距的线性关系；

（5）\textbf{TCP 遮挡}（C11--C13）：经实时帧流注入遮挡，验证 COAST 机制；

（6）\textbf{摄像头}（C14）：验证 USB 摄像头输入，默认跳过，需要时手动启用。

每个用例写清输入源、参数、期望指标与判定规则。框架按顺序执行，收集 CSV，算出锁定率、航迹保持率、首锁时延、置信度均值、距离范围与处理帧率，最后汇总成表。判定线这样划：基线用例的锁定率不低于 80\%，TCP 遮挡用例的航迹保持率不低于 70\%，特性刻画类用例只统计、不判定。

\subsubsection{测试结果}

用例结果在后面的实验部分统一给出。这里只说框架的两处设计：指标口径统一，所有用例共用同一套计算函数，人工统计的差异被排除在外；失败可复现，输入、参数与随机种子都记录在案，出了问题单独重跑即可。

\section{部署与运行维护}

\subsubsection{运行环境}

开发与测试环境为 Windows 11 + WSL2（Ubuntu 24.04），GPU 为 RTX 4060，Python 3.12，PySide6 6.x，PyTorch 2.x，Ultralytics 8.x，OpenCV 4.x。仿真跑在 WSL 里，界面经由 WSLg 显示。

\subsubsection{启动脚本}

系统提供一键启动脚本，按序拉起闭环与平台。脚本固化了几项环境变量：

（1）\texttt{DISPLAY=:0} 与 \texttt{QT\_QPA\_PLATFORM=xcb}：指定 WSLg 显示；

（2）\texttt{QTWEBENGINE\_DISABLE\_SANDBOX=1}：关闭 QtWebEngine 沙箱，渲染进程才不会在启动时失败；

（3）\texttt{QTWEBENGINE\_CHROMIUM\_FLAGS}：启用软渲染、禁用 GPU，WSLg 下地图空白的问题由此解决。

启动方式必须用 \texttt{setsid}，不能用 \texttt{nohup}。QtWebEngine 的 zygote 进程需要独立会话，\texttt{nohup+disown} 下渲染进程起不来，地图区域会是一片黑。这一点已写进部署文档。
